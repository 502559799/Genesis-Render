# 3D Gaussian Splatting

The demo includes a dedicated **Gaussian splat lab** (`--scene gaussian`,
`--lab gaussian`).  The goal of this iteration is a working, backend-portable
splat viewer and a clean extension point for a full 3DGS pipeline.

## 1. What is implemented

- **PLY parser** (`Gaussian::GaussianSplatCloud`) for
  - binary little-endian and ASCII PLY,
  - standard 3DGS attributes:
    `x y z nx ny nz f_dc_0..2 opacity scale_0..2 rot_0..3`,
  - plain colored point clouds (`x y z red green blue [alpha]`).
- **3DGS decoding**: SH DC → RGB (`0.5 + C0 * f_dc`), sigmoid opacity,
  exponential scales, normalized quaternion.
- **Per-frame projection**: world → view → clip, perspective-correct screen
  position and a screen radius derived from the largest splat scale.
- **Depth sorting** back-to-front on the CPU (painter's algorithm).
- **RHI-portable rasterisation**: each splat becomes an alpha-blended quad
  using a procedurally generated radial gaussian falloff texture, emitted
  through the existing `ui/batch` pipeline.  No compute shaders, storage
  buffers or backend-specific code are required.
- **Controls**: size, opacity, max screen radius, max splat count, depth sort,
  colour on/off, tint, auto orbit; live statistics (visible / drawn / sort and
  projection time).
- **Sample data**: `assets/splats/genesis_gaussians.ply` (12 000 splats: a
  double helix, a torus knot and a star shell), regenerated by
  `tools/gen_gsplat.py`.

## 2. Usage

```bash
python3 tools/gen_gsplat.py assets/splats/genesis_gaussians.ply --count 12000
./build/bin/genesis_demo --scene gaussian --lab gaussian
```

Drag with the left mouse button to orbit, wheel to zoom.  The lab panel can
load any `.ply` path at runtime.

## 3. Algorithm

```
for each splat:
    view_depth = dot(world_pos - eye, camera.forward)
    screen     = project(world_pos)
    radius_px  = max(scale) * size_scale * (0.5 * height / tan(fov/2)) / depth
sort visible splats by view_depth descending          // far -> near
for each splat:
    draw alpha quad [screen - r, screen + r] with gaussian falloff
```

The falloff texture is a 64×64 RGBA image with
`alpha = exp(-4.5 r²) * (1 - r⁴)` inside the unit circle, cached in the
`RenderScene` texture cache.  The quads are drawn after transparent geometry
(`CameraEvent::Overlay`), so they are composited over the rendered frame.

## 4. Why this is an approximation

A production 3DGS renderer evaluates the **projected 2D covariance** of each
3D Gaussian and rasterises anisotropic, oriented ellipses.  This iteration
uses isotropic screen-space quads because:

1. The RHI intentionally exposes only the feature set shared by GL 4.1 /
   Vulkan 1.1 / Metal.  It has no compute pipeline, storage buffers or
   `drawIndirect`, which a GPU sorter and tile-based splat rasteriser need.
2. Adding a new anisotropic splat shader requires regenerating GLSL / SPIR-V /
   MSL with `glslang` + `SPIRV-Cross`; the repository ships generated shaders
   and the toolchain is optional in this environment.
3. Screen-space painter's sorting is correct for a single view and avoids
   per-splat depth writes (3DGS needs alpha-correct compositing, not z-buffer).

The viewer is still useful to inspect datasets, test camera framing, sorting
and opacity, and to serve as the integration point for the full renderer.

## 5. Roadmap / extension points

| Step | Change |
|---|---|
| Anisotropic splats | Add a `splat.vert/frag` shader: pass 3D mean, 3×3 covariance, opacity; compute `J Σ Jᵀ` in the vertex shader and expand an oriented quad.  Generate SPIR-V + MSL with `scripts/build_shaders.py`. |
| Spherical harmonics | Upload SH coefficients (degree 0–3) and evaluate them against the view direction in the shader.  The PLY parser already reads `f_dc_*`; add `f_rest_*`. |
| GPU sort | Add a storage-buffer/compute RHI extension (or a CPU radix sort for 100k–1M splats); the current `std::sort` is the only scaling limit. |
| Depth interaction | Render splats into the scene pass with depth testing, or use a weighted-blended OIT pass; today they overlay after transparency. |
| Performance | The current path records one command per splat.  Batch all quads into a single vertex buffer (the batch executor already merges them) or feed a single instanced draw. |
| Large scenes | Streaming / chunked PLY loading and frustum culling per chunk. |

## 6. Performance notes

The software rasteriser used in this container (llvmpipe) renders 12 000
splats at ~15 fps at 1280×720; a hardware GPU is fill-rate bound only by the
splat footprint.  Reduce **max radius**, **size** or **max splats** in the lab
panel for weaker GPUs.
